## 1. 주제·차별성

**Q1. 왜 이 주제를 골랐나요? 전공과 어떻게 연결되나요?**
- 답: SNS마케팅 현장에서 가장 흔한 법적 위험이 광고 표시입니다. 상위 인플루언서 광고 글도 대가를 밝힌 비율이 29.9%뿐이고, 공정위가 5년간 찾은 의심 게시물이 약 10만 9천 건입니다. 마케팅의 두 주체인 인플루언서와 광고주가 모두 쓸 수 있는 도구로 풀었습니다. 캠페인 운영 순서(모집 → 섭외 DM → 선발 → 게시 → 검수 → 수정 요청)도 그대로 화면에 반영했습니다.
- 근거: `06_보고서.md` 1·2절, `결과보고서/00_양식항목별_초안.md` "반영한 전공 요소"

**Q2. 비슷한 서비스가 이미 있지 않나요?**
- 답: 2026-11-17 웹 검색으로는 한국 기준으로 올리기 전에 점검하는 도구를 찾지 못했습니다. 가장 비슷한 건 미국 PostEverywhere의 FTC 점검기인데, 미국 기준이라 "#ad"를 정답으로 봅니다. 한국 기준에서는 외국어 표현이 부적절합니다. 그리고 고친 글을 만들어 주는 도구는 없었습니다. 다만 찾지 못했다고 없다고 단정하지는 않습니다.
- 근거: `06_보고서.md` 2-3 유사 서비스 비교
- 주의: **"없다" 대신 "찾지 못했다"**

**Q3. 앱을 왜 두 개로 나눴나요? 하나로 합치면 안 되나요?**
- 답: 쓰는 사람과 때가 다릅니다. 크리에이터는 글 1개를 올리기 전에 점검하고 고친 글을 받습니다. 광고주는 올라온 뒤 여러 게시물을 일괄 검수하고, 수정 요청과 조치 상태, 다음 행사 섭외까지 관리합니다. 대신 점검 규칙은 원본 하나를 복사해 쓰기 때문에 두 앱의 판정은 항상 같습니다. 애드체크를 쓰지 않는 인플루언서의 글도 광고주 앱에서 잡을 수 있습니다.
- 근거: `06_보고서.md` 3절, `01_PRD.md` 6 "일관성"

**Q4. 공정위가 이미 단속하는데 이 앱이 왜 필요하죠?**
- 답: 공정위 점검은 이미 올라간 글을 적발한 뒤 시정을 요청하는 사후 방식입니다. 적발 유형 83.2%가 "어디에·어떤 말로"를 몰라서 생기는 문제라, 올리기 전에 알려 주면 막을 수 있습니다. 단속에 앞서 예방하는 단계를 더하는 것입니다.
- 근거: `06_보고서.md` 2-2, `05_향후계획.md` 5절

## 2. 법적 기준의 정확성 (공정위 추천·보증 심사지침)

**Q5. 점검 결과에 법적 효력이 있나요?**
- 답: 아니요. 공정위 「추천·보증 등에 관한 표시·광고 심사지침」을 바탕으로 한 참고용 점검이고, 법률 자문이 아닙니다. 점검 화면 하단에도 이 문구를 넣었습니다. 향후 계획에 점검 규칙과 개인정보 처리방침의 법률 검토를 넣었습니다.
- 근거: `01_PRD.md` 6 "고지", 9 "가정과 위험", `05_향후계획.md` 6절

**Q6. 규칙 6개는 심사지침의 어떤 내용을 반영했나요?**
- 답: 2024년 9월 시행 개정 지침의 핵심 두 가지, "어떤 말로"와 "어디에"입니다. 한글 '광고·협찬' 표시 여부, "내돈내산" 같은 반대 표현, 첫 부분(인스타 앞 40자, 블로그·유튜브 제목·첫 줄)에 있는지, thanks to·#ad 같은 애매하거나 외국어인 표현, 해시태그 더미 속에 묻혔는지, 받은 대가를 적었는지입니다. 적발 유형 상위 3개인 위치·미표시·표현에 그대로 대응합니다.
- 근거: `06_보고서.md` 5-1 규칙 표, `02_기술설계.md`

**Q7. "인스타그램 40자"는 어디서 나온 기준인가요?**
- 답: 지침에 적힌 숫자가 아니라, 인스타그램이 '더보기' 전에 앞부분 약 두 줄만 보여 준다는 점을 근사한 값입니다. 지침은 '더보기'를 눌러야 보이는 표시를 인정하지 않기 때문에, 그 앞에 표시가 있는지를 보도록 정했습니다. 화면 크기에 따라 달라질 수 있어 앞으로 실제 사용자 데이터로 조정할 부분입니다.
- 근거: `src/data/rules.ts`(INSTAGRAM_VISIBLE_CHARS = 40, "'더보기' 전에 앞부분 약 2줄"), `06_보고서.md` 2-2 기준 강화

**Q8. 심사지침이 바뀌면 어떻게 하나요?**
- 답: 규칙 파일 하나(`rules.ts`)만 고치면 두 앱에 같이 반영됩니다. 광고주 앱은 판정을 저장하지 않고 매번 계산해서, 지난 게시물도 새 기준으로 바로 다시 판정됩니다.
- 근거: `06_보고서.md` 5-1, `05_향후계획.md` 3절 "규칙 갱신"

## 3. 규칙 엔진의 한계·오탐

**Q9. AI를 쓰지 않고 규칙으로 판정한 이유는?**
- 답: 세 가지입니다. 같은 글이면 결과가 항상 같고, 1초 안에 즉시 나오고, 글을 외부 서버로 보낼 필요가 없습니다. 법 기준을 점검하는 도구라 결과가 매번 달라지면 신뢰할 수 없다고 봤습니다.
- 근거: `01_PRD.md` 6 "신뢰성·성능", 8 "범위 밖: AI 문장 생성"

**Q10. 오탐(잘못 잡는 경우)이나 미탐은 없나요?**
- 답: 있을 수 있습니다. 단어와 위치로 판정하기 때문에, 예를 들어 '광고'라는 단어가 다른 뜻으로 첫 줄에 쓰여도 표시로 볼 수 있고, 지침에 없는 새 표현은 놓칠 수 있습니다. 이미지나 영상 속 표시도 아직 보지 않습니다. 그래서 결과를 참고용으로 안내하고, 대회 직후 학생 10명·가게 사장님 3명 검증에서 "고친 글로 적합이 된 비율"을 측정해 규칙을 보완할 계획입니다.
- 근거: `src/data/rules.ts`(DISCLOSURE 정규식이 '광고'·'협찬' 등 단어를 찾음), `05_향후계획.md` 1절 한계·4절 일정, `01_PRD.md` 7 성공 지표
- 정직하게: 지금 측정한 건 **예시 4종 모두 기대 판정**까지다. 실제 게시물 대량 테스트는 아직 안 했다.

**Q11. 대가 없이 산 제품 후기도 위반으로 잡나요?**
- 답: 아니요. "받은 대가"를 '없음(내돈내산)'으로 고르면 표시 의무가 없으므로 적합으로 판정합니다.
- 근거: `06_보고서.md` 5-1 "대가 없음이면 적합"

**Q12. 이미지·영상(릴스·쇼츠) 속 표시는요?**
- 답: 지금은 글만 점검합니다. 숏폼은 캡션보다 영상 첫 장면의 자막·음성이 중요해서, 화면 스캔과 같은 방식으로 첫 장면을 읽어 처음 몇 초 안에 표시가 있는지 보는 기능을 계획에 넣었습니다. AI 가상 인플루언서 표시 규칙도 추가할 예정입니다.
- 근거: `05_향후계획.md` 3절

## 4. OCR 정확도·카메라 (화면 스캔)

**Q13. 화면을 찍어서 읽는 기능은 왜 필요하고, 정확도는?**
- 답: 회의실 모니터나 인플루언서 휴대폰으로 게시물을 볼 땐 글을 복사할 수 없습니다. 화면을 찍으면 깜빡임 줄무늬·모아레·손떨림이 생겨서 8장을 130ms 간격으로 찍고, 선명도와 줄무늬 점수로 가장 좋은 장면을 고릅니다. 예시 6장 실험에서 추천 장면은 글자 100% 일치(신뢰도 90%), 많이 흐린 장은 0~1%였습니다. 한 장만 찍으면 실패할 수 있다는 근거입니다.
- 근거: `advertiser/docs/02_기술설계.md`, `06_보고서.md` 5-2

**Q14. 100%는 예시 데이터 아닌가요? 실제 촬영에서는요?**
- 답: 맞습니다. 앱에 넣은 예시 화면 6장 기준입니다. 실제 촬영 정확도 목표는 90% 이상으로 잡았고, 아직 측정하지 않았습니다. 흐린 사진·작은 글씨에서는 정확도가 떨어지는 한계가 있어, 기울기·원근 보정, 글자 영역 자르기, 여러 장 결과 합치기를 개선 계획에 넣었습니다. 인식이 안 되면 사진을 보며 직접 입력할 수 있습니다.
- 근거: `01_PRD.md` 7 "스캔 인식 정확도", `05_향후계획.md` 1·3절

**Q15. 합성본은 왜 추천 장면보다 낮나요?**
- 답: 손떨림으로 장마다 위치가 어긋나서 처음엔 36%였습니다. 합성 전에 ±5픽셀 범위에서 위치를 맞추게 고쳐 81%가 됐습니다. 그래서 1위 추천 장면과 합성본을 둘 다 보여 주고 고를 수 있게 했습니다.
- 근거: `06_보고서.md` 7절, `advertiser/docs/02_기술설계.md`

**Q16. 촬영한 사진은 어디로 가나요? 카메라가 안 되면요?**
- 답: 사진은 휴대폰 밖으로 나가지 않습니다. 한글 OCR(tesseract.js)도 브라우저 안에서 돌고, 처음 한 번만 한글 언어 데이터를 받아 저장합니다. 카메라는 https에서만 켜져서 보안 연결일 때만 버튼을 보여 주고, 아니면 사진 여러 장 불러오기나 예시 화면으로 대체합니다. 권한 거부·카메라 없음도 안내합니다.
- 근거: `advertiser/docs/02_기술설계.md` "OCR·카메라", `01_PRD.md` 6 "대체 경로"

## 5. 개인정보·데이터 저장

**Q17. 데이터는 어디에 저장되나요? 개인정보는 안전한가요?**
- 답: 모든 데이터는 각 휴대폰 브라우저의 localStorage에만 저장됩니다. 서버·로그인·회원가입이 없어서 아직 공개하지 않은 협찬 글이 휴대폰 밖으로 나가지 않습니다. 개인정보를 수집하지 않으니 유출될 정보도 없습니다.
- 근거: `05_향후계획.md` 1절, `결과보고서/02_데이터아키텍처.md` 8절

**Q18. 그럼 기기를 바꾸면 기록이 사라지지 않나요?**
- 답: 네, 그게 지금의 한계입니다. 그래서 3단계 로드맵을 세웠습니다. 1단계는 서버 없이 JSON 파일로 백업하고, 2단계는 글 원문·업체명·계정 없이 플랫폼·문제 항목·점수만 모으는 익명 통계(첫 화면 안내, 끄기 가능), 3단계는 로그인과 클라우드 저장으로 수집 동의, 90일 뒤 자동 삭제, 원문 미저장 또는 암호화, 탈퇴 시 즉시 삭제를 지킵니다. 로그인 없이 쓰는 지금 방식은 계속 남깁니다.
- 근거: `05_향후계획.md` 2절

**Q19. 광고주 앱의 크리에이터 DB에는 연락처가 들어가는데요?**
- 답: 광고주가 자기 휴대폰에 직접 입력하는 정보이고, 지금은 그 기기 브라우저에만 저장되어 서버로 가지 않습니다. 팀 공유가 필요해지는 3단계에서는 처리방침과 동의, 보관 기간을 갖춘 뒤 클라우드로 옮길 계획입니다. 시연 데이터는 샘플입니다.
- 근거: `01_PRD.md` B-6, `05_향후계획.md` 2절, `결과보고서/02_데이터아키텍처.md` 8절

## 6. 수익 모델·사업성

- 근거: `결과보고서/00_양식항목별_초안.md` "한계 및 개선 계획", `01_PRD.md` 8 "유료 결제·광고주별 옵션", `06_보고서.md` 2-3 차별점
- 주의: **가격·매출 숫자는 문서에 없음 → 말하지 않는다**

**Q21. 광고주가 왜 돈을 내고 쓰죠?**
- 답: 뒷광고가 적발되면 광고를 맡긴 사업자도 제재 대상이 될 수 있습니다. 지금은 게시물을 하나씩 열어 보고 수정 요청 문구를 매번 새로 쓰는데, 일괄 검수와 메시지 자동 작성, 섭외 DM과 선착순 선발까지 한곳에서 해 줍니다.
- 근거: `06_보고서.md` 2-1, `01_PRD.md` 1·2절

**Q22. 운영 비용은요? 누가 먼저 쓰나요?**
- 답: 지금은 서버가 없어 배포 비용만 들고, 2단계 익명 통계까지는 무료 요금 안에서 운영할 수 있다고 봤습니다. 대회 직후 11월 말까지 SNS마케팅 전공·체험단 활동 학생 10명과 동네 가게 사장님 3명이 써 보고, 2027년 상반기 교내·지역, 하반기 대행사·소상공인 단체로 넓힐 계획입니다.
- 근거: `05_향후계획.md` 4·6절

## 7. AI 활용 방식

**Q23. AI를 어떻게 썼나요? 코드를 직접 이해하고 있나요?**
- 답: Claude Code로 기획 검토, 유사 서비스 조사, 코드, 디버깅, 배포, 문서를 함께 했습니다. 대회 전에 규칙 파일(CLAUDE.md)과 문서 템플릿, 자동 오류 검사, 프롬프트 자동 기록을 미리 준비했습니다. 코드를 바로 시키기보다 "누가 쓰나?", "비슷한 앱이 있나?", "DB는 어떻게 하지?"를 먼저 물었고, 그 답에서 광고주용 앱과 데이터 로드맵이 나왔습니다. 규칙 엔진은 한 함수(runCheck)로 분리돼 있어 판정 이유를 설명할 수 있습니다.
- 근거: `06_보고서.md` 6절, `결과보고서/00_양식항목별_초안.md` "활용 AI 도구"
- 도구: Claude Code(데스크톱 앱), 팩트챗, Claude Code 내장 웹 검색

**Q24. 프롬프트를 몇 번 썼나요?**
- 답: 자동 기록 분석으로 09:37~10:53 사이 크리에이터 앱 쪽 프롬프트가 24개였습니다. 이 중 20개가 직접 입력이고 4개는 다른 세션 완료 알림 같은 자동 메시지입니다. 광고주 앱 화면 스캔은 메인 세션이 넘긴 작업 지시서 1건(5,142자)으로 기능 전체를 만들었습니다.
- 근거: `06_보고서.md` 6-2, `docs/analysis/요약.md`
- 주의: 분석은 10:53까지 기준. 이후 기록(협업 기능·보고서)은 포함 안 됨

**Q25. AI가 만든 코드의 오류는 어떻게 잡았나요?**
- 답: 기능 하나를 끝낼 때마다 타입 검사·린트·빌드(`npm run check`)를 돌렸고, 작업이 끝날 때 훅이 자동으로 한 번 더 검사했습니다. 휴대폰 폭 375px 화면에서 시연 순서를 직접 돌려 30점 → 100점, 38% → 50%를 확인했습니다.
- 근거: `06_보고서.md` 7절, `03_작업목록.md`

**Q26. 막혔던 문제는?**
- 답: 화면 스캔 합성본이 흐려 OCR이 36%였는데, 합성 전 위치 맞추기를 넣어 81%로 올렸습니다. 글줄까지 줄무늬로 잡히는 문제는 합성본과의 차이로 측정해 해결했습니다. 휴대폰에서 카메라가 안 켜지는 건 https 문제여서 대체 경로를 만들었습니다.
- 근거: `06_보고서.md` 7절

## 8. 기술 선택

**Q27. 왜 앱이 아니라 웹앱인가요?**
- 답: 설치 없이 링크나 QR 하나로 휴대폰에서 바로 열립니다. 처음 협찬을 받은 학생에게는 가입·설치 없는 점검이 가장 큰 장점이라고 봤습니다. 홈 화면 설치형(PWA)과 오프라인 첫 실행은 향후 계획에 있습니다.
- 근거: `05_향후계획.md` 2·3절, `01_PRD.md` 머리 표

**Q28. 기술 스택은?**
- 답: Vite + React 19 + TypeScript, Tailwind CSS v4, 차트는 recharts, OCR은 tesseract.js 7, 저장은 localStorage, 배포는 Vercel입니다. 타입 검사로 AI가 만든 코드 오류를 빌드 단계에서 잡을 수 있어서 TypeScript를 골랐습니다. 외부 API가 없어 네트워크가 끊겨도 점검이 됩니다.
- 근거: `06_보고서.md` 5절

**Q29. 사용자가 늘면 성능은요?**
- 답: 점검 계산이 각 사용자 휴대폰에서 일어나서 사용자가 늘어도 서버 부담이 없습니다. 서버가 필요해지는 건 2·3단계 통계와 클라우드 저장부터입니다.
- 근거: `06_보고서.md` 5절 구성도, `05_향후계획.md` 2절
